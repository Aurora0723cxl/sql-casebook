# 电商订单分析 · SQL 案例库

11 个业务问题，一套可直接跑起来的 SQLite 库。**零配置**：不需要装 MySQL、不需要导数据，`python run.py` 一条命令就出结果。

写给谁看：招聘方想快速判断「这个人会不会用 SQL 回答业务问题」；我自己复习窗口函数和口径。

> 数据是**合成的**（`seed.py` 生成，seed=42 可复现），所以比率不要当行业基准。结构和坑是按真实业务埋的。

## 30 秒跑起来

```bash
python seed.py      # 生成 data.db（约 6.5 MB，5 秒）
python run.py       # 依次执行 11 条查询，打印结果并写出 RESULTS.md
python run.py --bench   # 附带一次索引前后对比实验
```

只依赖 Python 3 标准库里的 `sqlite3`，没有第三方包。

也可以用 `sqlite3` 命令行：

```bash
sqlite3 data.db < schema.sql
sqlite3 data.db < queries/q03_channel_funnel.sql
```

## 数据

| 表 | 行数 | 说明 |
|---|---|---|
| `users` | 1,500 | 注册日期、城市、注册渠道、年龄段 |
| `products` | 25 | 5 个品类 × 5 个 SKU |
| `orders` | 19,023 | 2025-01-01 ~ 2026-09-30，状态含 paid / refunded / cancelled |
| `events` | 112,176 | 用户级埋点：点击 / 加购 / 下单 / 支付 |
| `impressions` | 105 | 渠道 × 月的曝光汇总（来自广告后台，不是埋点） |
| `channel_spend` | 105 | 渠道 × 月的投放花费 |

两个刻意的设计：

1. **曝光和点击来自不同系统**。曝光是广告后台的汇总数，点击是埋点。混在一张表里 JOIN 就会重复计数——这是 Q3 的核心考点。
2. **大促和异常是真的**。2025-11（双 11）、2026-06（618）有峰值；美妆品类在 2026-03 的退款率被刻意抬高，用来测试异常检测能不能抓出来。

## 索引实验（`python run.py --bench`）

| 查询 | 建索引前 | 建索引后 | 提速 |
|---|---|---|---|
| `WHERE user_id = 1234` | 0.72 ms | 0.19 ms | **3.9×** |
| `ORDER BY created_at DESC LIMIT 100` | 1.67 ms | 0.19 ms | **9.0×** |
| `WHERE created_at >= '2026-01-01'` + 按月聚合 | 3.49 ms | 4.54 ms | **0.8×**（反而略慢） |

三条结论，第三条最容易被忽略：

1. 等值查找走索引，扫全表变 `SEARCH ... USING INDEX`。
2. 排序也能被索引救：索引本身有序，`ORDER BY created_at DESC LIMIT 100` 不用再建临时 B 树，而且只扫 100 行。
3. **范围查询 + 表达式分组时，索引不一定有用**。`GROUP BY substr(created_at,1,7)` 让 SQLite 必须先把 19,000 行全读出来算表达式，再建临时 B 树分组；索引只帮着定位起点，省不下大头。这种场景的正解是建**表达式索引**或预聚合到日/月表。

面试里能主动说出第 3 条的人不多。

## 我踩过的三个坑

**坑一：漏斗把曝光放大了。**
一开始写成 `impressions JOIN events ON channel AND month`，结果每个渠道的曝光数被乘以该渠道的事件行数，CTR 算出来 300%。正解是两边分别 `GROUP BY` 再 JOIN。

**坑二：跨年算留存，月份差算错。**
直接 `月 - 月` 在跨年时会得到负数（2026-01 减 2025-11 = -10）。改成 `年*12 + 月` 再相减，月份差才是连续的。

**坑三：复购率在订单粒度上算。**
`COUNT(*)` 在 orders 表里是订单数，不是用户数。先聚合到用户粒度（每人几单），再算「几单 >= 2 的人 / 总人数」，否则分母就错了。

## 面试怎么讲（30 秒版）

> 我做了一个 SQL 案例库，11 个业务问题，从日报到 RFM 分层都有。数据是我自己造的，因为重点不是数据，是口径：比如漏斗那张表，曝光来自广告后台、点击来自埋点，直接 JOIN 会把曝光放大好几倍，CTR 能算到 300%，所以两边必须分别聚合。另外我还做了索引对比，有一条范围查询加索引反而更慢，因为它要先算表达式再分组。

被追问时能接住的三个方向：

- **为什么用 SQLite？** 零配置，别人 clone 下来直接能跑；SQL 语法和 MySQL 差异只在少数函数，不影响思路。
- **RFM 的阈值怎么定的？** 用 `NTILE(4)` 分四档，是为了让四层人数可控；真实业务里应该按运营能覆盖的人数倒推，而不是机械四分。
- **这个结论能直接用于决策吗？** 不能。数据是合成的，比率没有业务含义；能用于决策的是**方法和口径**。

## 局限

- 数据合成，比率不可当行业基准。
- 只有退款状态，没有退款金额与原因，所以算不了净 GMV 与退款归因。
- 没有曝光到点击的明细链路（只有汇总数），所以做不了分素材/分人群的漏斗。
- 时间范围 21 个月，只够看同比，不够做季节性分解。
